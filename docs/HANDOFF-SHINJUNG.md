# 1단계 — 로컬을 Postgres 로

**왜:** 지금 로컬 SQLite / 운영 Postgres 입니다. 2026-08-12 에 `DATABASE_URL`
이 빠져 운영이 조용히 SQLite 로 떨어져 데이터가 날아간 사고가 그 틈에서
났습니다. 그리고 taxbriefing 표는 **스키마**(`tb`)에 들어가는데 SQLite 는
스키마를 지원하지 않습니다.

지금 재직 3명·휴가 1건이라 **지킬 데이터가 사실상 없습니다. 지금이 가장
쌉니다.**

할 일:

1. `docker-compose.yml` 에 postgres:16 하나 (없으면 만들기)
2. 로컬 `.env` 의 `DATABASE_URL` 을 그 Postgres 로
3. `database.py:18` 의 조용한 SQLite 폴백을 **막습니다** —
   운영 환경인데 `DATABASE_URL` 이 없거나 sqlite 면 **기동을 거부**하세요.
   조용히 잘못된 곳에 쓰는 것보다 안 뜨는 편이 낫습니다
4. 기존 SQLite 데이터가 필요하면 옮기고, 아니면 시드로 다시 만듭니다

확인: 기동 로그와 `GET /api/health` 의 `database` 값이 `postgresql` 인지.

# 2단계 — tb 스키마 받을 자리 만들기

taxbriefing 표 28개가 `tb` 스키마로 들어옵니다. **당신은 그 표를 만들지
않습니다** — taxbriefing 쪽 Alembic 이 만듭니다.

당신이 할 일은 **부딪히지 않게 하는 것**입니다.

1. Supabase 운영과 로컬 양쪽에 `CREATE SCHEMA IF NOT EXISTS tb;`
2. `database.py:1058` 의 `Base.metadata.create_all()` 이 `tb` 를 **안 건드리는지**
   확인하세요. 신정 `Base` 에는 taxbriefing 모델이 없으므로 원래 안 건드리는
   것이 맞지만, **실제로 확인하세요.** 기동 후 `tb` 에 신정 표가 생기면 안 됩니다
3. `_run_migrations()`(`database.py:825~`) 도 마찬가지입니다. `ALTER TABLE` 이
   스키마를 안 적으면 `search_path` 를 타므로, `search_path` 에 `tb` 가 들어가지
   않게 하세요

확인 방법 — 기동 후 이 질의가 **0** 이어야 합니다.

```sql
select count(*) from information_schema.tables
where table_schema = 'tb'
  and table_name in (select table_name from information_schema.tables
                     where table_schema = 'public');
```

## 옮길 때 반드시 지킬 것 — 잃기 쉬운 규칙

**이건 코드가 아니라 그동안 겪고 나서 알게 된 것들입니다.** 화면을 다시
짜면서 제일 잘 빠집니다.

### 종류에 따라 말을 바꾼다

법령 · 심판례 · 해석례 · 판례 · 법안 · 입법예고가 **각각 다른 문장**을
씁니다. 하나로 뭉치면 이런 것이 나옵니다.

    「…심판청구가 적법한지 여부 — 기각」이(가) 개정되어
    시행일은 원문 확인이 필요합니다.

심판례는 개정된 것이 아니고 시행일도 없습니다.

- **법령** — 공포일·시행일·달라지는 점·사업자가 할 일
- **심판례** — 결론(인용/기각…)·의결일·판단 요지. 시행일 없음
- **해석례·판례** — 회신일/선고일 하나뿐. 본문 없음. "이런 판단이 있다" 까지만
- **법안** — 발의자·소관위원회·처리결과. **시행일도 할 일도 쓰지 않습니다**
- **입법예고** — "아직 확정된 개정이 아닙니다" + 의견 제출 마감

### 상태 배지와 경고는 서버가 정한 것을 씁니다

`status_label` · `status_caveat` 를 API 가 내려줍니다. **화면에서 다시 만들지
마세요.** 심판례·해석례에는 둘 다 `null` 로 옵니다 — 진행 단계라는 것이
없기 때문입니다. `null` 이면 안 그리면 됩니다.

### 확정되지 않은 것에 [중요] 를 달지 않습니다

법안과 입법예고는 위험도가 LOW 로 옵니다. 세법 열 건이 같은 날 예고된 적이
있는데, 전부 [중요] 로 나가면 확정된 개정이 그 아래 묻힙니다.

### 예고를 확정된 것과 섞지 않습니다

「예고 단계」를 「최근 확정된 것」 **위**에 따로 둡니다. 같은 모양의 카드로
이어 붙이면 스크롤하다 「소득세법 일부개정법률안」을 이미 바뀐 것으로
읽습니다. **이 화면에서 가장 위험한 오해가 그것입니다.**

### 없는 값은 줄을 안 씁니다

"확인 필요" 로 채우지 마세요. 확인할 것이 없는데 있는 것처럼 읽힙니다.
시행일이 없으면 시행일 줄이 없습니다.

### 자른 것은 자른 사실을 적습니다

목록에서 몇 건을 뺐으면 "이 밖에 N건이 더 있습니다" 를 적습니다. 조용히
자르면 오늘 나온 게 그게 전부라고 믿습니다.

# 6단계 — 거래처 업종 (합치는 이유가 여기서 실현됩니다)

지금 `clients` 에 업종 칸이 없어서 **"음식점 3곳에 해당하는 개정" 이

## 두 가지를 같이 해야 합니다

**1. 업종 칸** — `industry_code` + `industry_name`.

자유 입력으로 두면 안 됩니다. "음식점" 과 "일반음식점" 이 다른 값이 되어
거를 수가 없습니다. **드롭다운**으로 고르게 하세요.

taxbriefing 업종 13개와 이어야 합니다. 표준산업분류를 쓸 거라면 그것과
taxbriefing 업종의 **대응표**가 따로 필요합니다.

    ALL 전 업종 공통 · FOOD 요식·음식점 · EDU 학원·교육 · RETAIL 도소매·유통
    BEAUTY 미용·서비스 · LODGING 숙박 · TRANSPORT 운수·배달
    FREELANCE 프리랜서·인적용역 · MEDICAL 의료·약국 · CONSTRUCTION 건설
    REALESTATE 부동산임대 · MANUFACTURING 제조 · CORPORATE 법인 일반

**2. 엑셀 일괄 등록에 업종 칸** — 99곳을 손으로 채우게 두면 안 채워집니다.
등록기에 칸을 같이 넣으세요.

## 담당이 한 사람에게 몰려 있습니다

99곳 **전부 한 사람 담당**입니다. 그러면 "김실장이 맡은 거래처 중 음식점" 이
아직 성립하지 않습니다. **담당 나누기가 업종 채우기와 같이 가야** 합니다.

`_my_client_ids()`(`routers_phase6.py:938`)와 `GET /api/clients?mine=true` 가
이미 있으니, 담당만 나뉘면 질의는 그대로 씁니다.
