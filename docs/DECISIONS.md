다음 명세서 개정에 반영한다(§1.5 우선순위 규칙에 따라 정식 개정 시 원본이 우선권을 되찾는다).

## ADR-001 — 텔레그램은 알림, 웹사이트는 기준 화면

**결정일** 2026-08-06 · **상태** 승인 · **결정자** 제품책임자

### 배경

명세서 §11.4는 채널을 이메일·알림톡·SMS·웹으로 규정하고, 웹을 "전체 근거와 정정 이력을
보존하는 기준 화면"으로 둔다. 실제 운영에서는 매일 아침 푸시 채널이 먼저 필요하고,
기존 사내 프로젝트(`ai-market-brief`)가 이미 텔레그램 봇으로 일일 발송을 운영 중이다.

### 결정

**텔레그램에 전문을 보내지 않는다.** 텔레그램은 요약 + 링크만 보내고, 상세는 웹으로 연결한다.

```
수집 → AI 분석 → 관리자 검수 → 사이트 게시 → 텔레그램 요약 + 링크 발송
```

| 채널 | 역할 | 담는 것 |
| --- | --- | --- |
| 텔레그램 | 알림 | 중요도, 대상, 상태, 시행일, 핵심 1~2줄, 할 일, 링크 |
| 웹사이트 | 기준 화면 | §10.3 표준 블록 12개 전부, 공식 출처, 근거, 정정 이력 |
| 이메일 | 일일·주간 브리핑 | 요약 묶음 + 링크 (미결 ① 확정 후) |
| 알림톡 | 2단계 | 승인 템플릿 (미결 ① 확정 후) |

### 근거

표·정책 단계·출처·시행일·대상 구분은 텔레그램 평문에서 깨진다. §10.4는
"현재 기준과 변경 예정 내용을 같은 문단에 혼합하지 않는다"를 요구하는데,
4096자 제한 안에서 이를 지키면서 근거까지 담을 수 없다.

무엇보다 **공식 출처 링크와 정정 이력은 보존돼야 한다**(§1.3 추적 가능성).
메시지는 수정할 수 없지만 웹 페이지는 정정 배너를 올릴 수 있다.

### 구현

- 렌더러: [`app/services/render/telegram.py`](../backend/app/services/render/telegram.py)
- 채널 어댑터: [`app/services/delivery/channels.py`](../backend/app/services/delivery/channels.py) `TelegramAdapter`
- `Channel.TELEGRAM` 추가. `openapi.yaml`의 `channels` enum은 미결 ① 확정 시 함께 갱신한다.
  그때까지 계약 파일은 손대지 않으며, `tests/contract/test_contract_parity.py`가 이 상태를 감시한다.

### 메시지 형태

```
[중요] 법인 업무용 차량 비용처리 기준 변경

대상: 법인사업자
상태: 시행 중
시행일: 2026년 9월 1일

핵심 내용
· 증빙 및 운행기록 기준이 변경됩니다.

사업자가 할 일
· 차량별 운행기록과 보험 가입조건을 확인하세요.

상세 내용 및 공식 출처 보기
https://taxbriefing.example/article/123
```

시행일 근거가 없으면 `시행일: 확인 필요`로 출력한다. 임의 날짜를 넣지 않는다(§10.4, AT-05).
확정되지 않은 상태에는 `상태: 입법·행정예고 (시행 확정 아님)`처럼 경고가 따라붙는다(AT-04).

## ADR-002 — MVP에서 일반 사용자 로그인을 제외한다

**결정일** 2026-08-06 · **상태** 승인

### 결정

콘텐츠는 **로그인 없이 공개**한다. 관리자만 로그인한다.

| 대상 | MVP |
| --- | --- |
| 일반 사용자 | 로그인 없음. 텔레그램·이메일 링크로 유입해 바로 열람 |
| 관리자 | 이메일+비밀번호 로그인, 2단계 인증 |

### 근거

회원가입·비밀번호 찾기·개인정보 동의·탈퇴·인증메일·보안관리를 MVP에 넣으면
개발 범위가 크게 늘고 사용자 이탈 지점이 생긴다. 12주 안에 §14.5 완료 정의를
만족하려면 수집·검증·검수·발송이라는 핵심 경로에 집중해야 한다.

### 로그인이 필요해지는 시점 (2단계)

내 사업자 유형 맞춤정보 · 관심 업종 설정 · 저장함 · 읽음 처리 · 맞춤 알림 ·
유료 구독 · 세무사무소별 고객 전용 콘텐츠

2단계에서는 비밀번호 대신 카카오/네이버 소셜 로그인 또는 이메일 인증 링크를 우선한다.

### 명세서에 미치는 영향

- §2.1 사용자 유형 중 "일반 구독자·법인 담당자"의 로그인 기능은 2단계로 이동
- §4.6~4.8 중 `FR-PER-001`(프로필), `FR-USR-003`(저장·읽음), `FR-USR-004`(수신설정)은 2단계
- `FR-USR-001`(오늘의 브리핑), `FR-USR-002`(콘텐츠 상세)는 **비로그인 공개**로 구현
- §12.4 수신동의는 텔레그램·이메일 구독 시점에만 필요하며, 웹 열람에는 필요 없다

### 구현

- 공개 API: [`app/api/v1/public.py`](../backend/app/api/v1/public.py) — 인증 의존성이 붙지 않는 유일한 라우터
- 공개 대상은 `PUBLISHED`/`MONITORING`/`CORRECTED` 상태로 **쿼리에서 강제** 제한한다.
  검수 전 초안이 공개 경로로 새는 것은 §1.3 위반이므로 필터를 옵션으로 두지 않았다.
- 검증: `tests/acceptance/test_public_and_telegram.py::test_unpublished_content_never_leaks`
  (7개 미공개 상태 전부에 대해 피드 미노출 + 상세 404 확인)

### 개인화는 어떻게 되나

로그인이 없으면 사용자별 개인화가 불가능하다. 그래서 MVP의 개인화는 두 층으로 나눈다.

1. **필터** — 사용자가 직접 고른다 (개인사업자/법인, 세무/노무/지원사업, 업종, 상태, 중요도)
2. **매칭 엔진** — 코드는 이미 완성되어 있다([`app/domain/personalization.py`](../backend/app/domain/personalization.py)).
   프로필이 생기는 2단계에 그대로 연결한다. AT-08(명시적 제외)·AT-10(수신철회)은 지금도 통과한다.

## ADR-003 — 관리자 권한은 3역할로 운영한다

**결정일** 2026-08-06 · **상태** 승인

### 결정

명세서 §12.2의 6개 역할 중 MVP에서 실제로 부여하는 것은 3개다.

| 운영 호칭 | 코드 역할 | 권한 |
| --- | --- | --- |
| 운영자 | `EDITOR` | 수집자료 확인, 콘텐츠 작성·편집, 근거 연결, 검수 요청 |
| 검수자 | `REVIEWER` | 세무 검수, 승인·반려, 정책상태·위험도 확정 |
| 최고관리자 | `SYSTEM_ADMIN` | 출처 레지스트리, 사용자·권한, 시스템 설정 |

`VIEWER`, `CAMPAIGN_MANAGER`, `TENANT_ADMIN`은 enum과 RBAC 표에 남겨두되 MVP에서는 부여하지 않는다.
B2B 화이트라벨(§4.9 FR-B2B)이 시작되면 `TENANT_ADMIN`부터 활성화한다.

### 바뀌지 않는 것

**`SYSTEM_ADMIN`은 승인할 수 없다.** 최고관리자여도 `POST /contents/{id}/reviews`는 403이다.
§12.2의 "검수 책임 자동 대체 불가"를 코드로 강제한 것이며,
`tests/acceptance/test_api_rbac.py::test_system_admin_cannot_review`가 지킨다.

한 사람이 운영자와 검수자를 겸해야 한다면 계정을 분리하지 말고 `REVIEWER`를 준다
(`REVIEWER`는 편집 권한 `EDIT_ROLES`에도 포함된다). 계정 공유가 감사 추적을 망가뜨리는 것보다 낫다.

## ADR-004 — 배포는 프론트/백엔드를 분리한다

**결정일** 2026-08-06 · **상태** 제안 · **미결 ⑥과 연결**

### 배경

프론트엔드를 개인 Vercel에 올리는 방안이 제기되었다.

### 결정

**프론트엔드는 Vercel, 백엔드는 별도 호스트**로 나눈다.

| 구성요소 | 권장 | 이유 |
| --- | --- | --- |
| 공개 웹 + 관리자 웹 (Next.js) | **Vercel** | 정적·SSR 배포에 최적. PWA도 그대로 동작 |
| API (FastAPI) | Railway / Render / Fly.io | 상시 프로세스, 타임아웃 제약 없음 |
| PostgreSQL | Neon / Supabase / 호스트 제공 DB | 시점복구 필요 (§NFR-012) |
| 수집 워커·스케줄러 | GitHub Actions cron 또는 워커 프로세스 | 아래 참조 |
| 객체 스토리지 | S3 호환 (원문·첨부·발송 스냅샷) | 미결 ⑧ |

### Vercel에 백엔드까지 올리지 않는 이유

- **수집 워커가 돌 곳이 없다.** Vercel 함수는 요청-응답 수명주기에 묶여 있어
  §6.3 파이프라인(수집 → 첨부 추출 → 클러스터링)처럼 수 분 걸리는 작업에 맞지 않는다.
- **타임아웃.** HWP/스캔 PDF 추출은 수십 초가 걸릴 수 있다(§15.4 리스크).
- **DB 커넥션.** 서버리스는 요청마다 커넥션을 새로 잡아 PostgreSQL 커넥션이 고갈되기 쉽다.
  풀러(pgBouncer/Neon 풀링)를 붙여야 하는데, 상시 프로세스면 필요 없는 복잡도다.

### 스케줄러

`ai-market-brief`가 이미 GitHub Actions cron으로 KST 06:30 발송을 운영하고 있다.
같은 방식을 재사용하는 것이 가장 빠르다.

```yaml
# 수집: 업무시간대 2시간 간격
- cron: '0 0,2,4,6,8 * * 1-5'   # UTC → KST 09,11,13,15,17시
# 일일 브리핑 발송: KST 07:00
- cron: '0 22 * * 0-4'
```

발송 시각은 §11.3 "평일 아침"과 §12.4 야간 발송 제한을 함께 고려해 확정한다.

### 확정 필요

호스트 선택은 미결 ⑥(클라우드 계정)에 묶여 있다. 한국 리전 요구(§6.1)가
법적 요건인지 성능 요건인지에 따라 선택지가 달라지므로, 제품책임자 확인이 필요하다.
