# 9. AI 분석·요약 명세

> 원본: 통합개발명세서 §9 · 정본 계약: [`docs/contracts/ai_output_schema.json`](../contracts/ai_output_schema.json)

## 9.1 AI 사용 경계

| 구분 | 내용 |
| --- | --- |
| 허용 | 원문 요약, 구조화 추출, 상태 후보, 대상·태그 후보, 변경점 비교, 경고 생성 |
| 조건부 | 사업자 영향과 행동사항은 **원문 및 검증된 규칙에 근거할 때만** 생성 |
| 금지 | 세액 확정, 개인별 법률·세무 판단, **원문에 없는 숫자·날짜·예외·기관명 생성** |
| 필수 | 모든 주요 필드에 `evidence` 또는 `missing_reason` 반환 |
| 필수 | 충돌·불명확·추정이 필요한 경우 `null`과 `warning` 반환 |
| 필수 | 검토·발의·예고를 시행 확정으로 표현하지 않음 |

## 9.2 프롬프트 입력 구성

- 대표 원문과 관련 공식 원문 목록
- 원문별 출처 등급, 기관, 게시일, 수집일, URL
- 첨부파일 추출 텍스트와 페이지 또는 문단 위치
- 기존 콘텐츠가 있으면 이전 버전과 diff
- 현재 기준일과 사용자 표시 시간대
- 정책 상태 enum과 태그 사전
- 출력 JSON Schema와 금지 규칙

프롬프트 템플릿: [`backend/app/services/ai/prompts/analysis_v1.md`](../../backend/app/services/ai/prompts/analysis_v1.md)

## 9.3 출력 필드

| 필드 | 설명 |
| --- | --- |
| `title` | 사업자용 제목 |
| `one_line_summary` | 한 줄 요약 |
| `legal_status` | 정책 법적 상태 **후보** |
| `announcement_date` | 발표일 |
| `promulgation_date` | 공포일 |
| `effective_date` | 시행일 |
| `application_period` | 신청기간 |
| `affected_users` | 적용 대상 |
| `excluded_users` | 제외 대상 |
| `changes` | 기존 대비 변경점 |
| `business_impact` | 세금·비용·신고·노무 영향 |
| `required_actions` | 지금 해야 할 일 |
| `deadlines` | 마감·신고 일정 |
| `risk_level` | 콘텐츠 위험도 |
| `topics` | 세목·정책 분야 |
| `warnings` | 충돌·불확실·추가검토 |
| `evidence` | 필드별 `source_version_id`와 `locator` |

## 9.4 출력 검증 규칙 (하드 게이트)

| # | 규칙 | 구현 |
| --- | --- | --- |
| V1 | JSON Schema 검증 실패 시 **저장하되** 검수 큐에 표시하고 자동 진행 금지 | `ai_analyses.status='SCHEMA_FAILED'`, `validation_result`에 오류 저장 |
| V2 | 날짜가 원문에 존재하지 않으면 `null`이어야 함 | 날짜 필드에 값이 있으면 해당 `field_name`의 evidence 필수 |
| V3 | `PROMULGATED`/`EFFECTIVE` 상태는 **A등급 근거 없이는 통과 금지** | 게이트 G5 + `legal_status` 교차검증 |
| V4 | `HIGH`/`CRITICAL` 위험도는 전문가 승인 필수 | 게이트 G6 |
| V5 | evidence가 없는 `required_actions`는 자동 삭제 또는 검수 경고 | 스키마상 `evidence_ids` minItems=1 이므로 스키마 단계에서 차단 |
| V6 | 두 원문이 충돌하면 `conflict` 항목을 생성하고 어느 쪽도 임의 선택하지 않음 | `evidence[].support_type='CONFLICT'` + `warnings[]` |
| V7 | 모델 출력은 HTML을 직접 생성하지 않고 구조화 데이터에서 채널 템플릿으로 렌더링 | 렌더링은 `app/services/render/`에서만 |

구현: [`app/services/ai/validation.py`](../../backend/app/services/ai/validation.py)

### 스키마 계약에서 확인된 이슈와 구현 결정

| # | 초안 상태 | 구현 결정 |
| --- | --- | --- |
| S-01 | `evidence[].source_version_id`가 `type: string` (format 없음) | UUID 문자열로 검증 강화. 요청의 `source_version_ids`에 속하지 않으면 반려 |
| S-02 | `evidence_ids`가 `evidence[].id`를 참조하지만 스키마로는 강제 불가 | 참조 무결성을 애플리케이션에서 검증 (`dangling evidence_ids` → V1 실패) |
| S-03 | `missing_reason`이 §9.1에서 필수라고 하나 스키마에 필드 없음 | `warnings[]`의 `code='MISSING_EVIDENCE'` + `related_fields`로 대체. §9.1 문구를 이에 맞춰 해석 |
| S-04 | `affected_users`/`excluded_users`가 자유 문자열 배열 — 개인화 매칭 불가 | AI는 자유 문자열로 제안, 운영자가 `content_tags`로 정규화. 개인화는 태그만 사용 |
| S-05 | `application_period`가 `null` 가능하나 객체일 때 `start`/`end` 모두 required (nullable 허용) | 그대로 유지. `{start: null, end: null}`은 "신청기간 개념은 있으나 미확정" |
| S-06 | `announcement_date` 등 날짜 필드가 최상위 `required`에 없음 | 필드 자체는 optional, 단 **값이 있으면 evidence 필수** (V2) |

## 9.5 AI 실행 이력 저장

| 항목 | 저장값 |
| --- | --- |
| `prompt_template_id` | 템플릿 ID |
| `prompt_version` | semantic version |
| `model_provider` / `model_name` | 제공자와 모델명 |
| `input_hash` | 정규화 입력 해시 |
| `schema_version` | 출력 스키마 버전 |
| `temperature`/settings | 재현 설정 |
| `token_usage` / `cost_amount` | 비용 |
| `latency_ms` | 지연시간 |
| `validation_result` | 스키마·정책 게이트 결과 |

> `input_hash`는 멱등성 키로도 쓴다. 동일 입력 + 동일 프롬프트 버전 + 동일 모델이면 재분석하지 않고 기존 결과를 반환한다.

## 9.6 골든셋 평가

세무전문가가 최소 100건을 라벨링하고, **날짜·상태·대상·행동사항·근거 정밀도를 별도로 측정**한다.
자동 점수 외에 전문가 오류등급을 기록한다. 케이스 구성은 [13. 테스트·인수 기준](13-testing.md#134-골든셋-케이스) 참조.
