# 13. 운영·모니터링·장애대응

> 원본: 통합개발명세서 §13

## 13.1 관측 지표

| 영역 | 지표 |
| --- | --- |
| 수집 | 출처별 성공률, 신규·변경 건수, 평균 지연, 파서 오류 |
| 검증 | 미검증 건수, A/B 근거 연결률, 상태 불명 건수 |
| AI | 스키마 통과율, 경고율, 재분석률, 비용, 지연 |
| 검수 | 대기 건수, 평균 처리시간, 반려율, 검수자 부하 |
| 발송 | 성공, 반송, 수신거부, 공급자 오류, 지연 |
| 사용 | 열람, 클릭, 저장, 상담, 관심없음 |
| 품질 | 정정 건수, 중대 오류, 원인, 재발방지 |

## 13.2 장애 등급

| 등급 | 조건 | 대응 |
| --- | --- | --- |
| **P1** | 잘못된 고위험 세무정보 대량 발송, 개인정보 유출 의심 | **즉시 발송중지**, 책임자 호출, 영향분석, 정정·신고 검토 |
| P2 | 주요 출처 6시간 이상 수집 실패, 발송 성공률 급락 | 1시간 내 대응 |
| P3 | 단일 출처 파서 오류, AI 스키마 실패 증가 | 영업일 내 수정 |
| P4 | 개선 요청, 비핵심 UI 문제 | 백로그 |

> P1 대응의 "즉시 발송중지"는 수동 절차가 아니라 **킬 스위치 API**여야 한다.
> `POST /admin/delivery-halt` — 진행 중 캠페인을 전부 `CANCELED`로 전환. (S3 구현 예정)

## 13.3 정정 프로세스

1. 오류 또는 변경 신고 접수
2. 콘텐츠·발송 영향 범위 **잠금**
3. 전문가가 사실과 위험도 판정
4. 정정본과 차이 설명 작성
5. 영향 대상 추출과 채널 선택
6. 정정 승인 후 재발송
7. 기존 웹 콘텐츠에 정정 배너와 버전 표시
8. 원인분석 및 규칙·프롬프트·검수체계 개선

목표: 중대 오류 인지 후 **2시간 이내** 정정 발송 (§1.4 성공지표).

## 13.4 백업·복구

- DB 자동 백업과 시점복구 활성화
- 객체 스토리지 버전관리와 수명주기 정책
- 배포 전 마이그레이션 백업
- 분기별 복구 테스트와 결과 기록
- **RPO 24시간 이하, RTO 4시간 이하**를 MVP 기준안으로 설정 후 사업 요구에 따라 강화

검증: AT-15 (DB 복원 후 최근 승인 콘텐츠와 발송 이력 일치)
