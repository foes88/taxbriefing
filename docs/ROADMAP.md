# 개발 계획

세무 실무자가 **다른 직원보다 앞서서** 정책에 대응하도록 돕는 것이 이
서비스의 목적이다. 아래 순서는 그 목적에 가까운 것부터다 — 만들기 쉬운
것부터가 아니다.

## 지금 서 있는 자리

| | |
| --- | --- |
| 정책·법령 | 203건 (시행 예정 53건 포함) |
| 심판례 | 49건 (결론 인용 6 · 일부인용 3 · 기각 36) |
| 국회 법안 | 62건 |
| 뉴스 | 77건 (세무 무관 35건은 지웠고, 앞으로 안 담는다) |

| 테스트 | 380건 |

기반은 섰다. 남은 일은 **판단을 돕는 층**을 올리는 것이다.

## 확인된 한계 (다시 파지 말 것)

여기 적힌 것은 시도해 보고 막힌 것이다. 같은 길을 다시 파면 시간만 든다.

**법제처 `oldAndNew` 는 법령당 최신 대조표 1건만 준다.**
`query=소득세법` → `totalCnt=3` (법 / 시행령 / 시행규칙 각 1건).
`nw`·`section`·`sort` 를 바꿔도 같다. 지난 개정의 신구법 대조표는
이 API 로 얻을 수 없다. 그래서 49건은 대조표 없이 남는다.

**네이버 검색 API 는 신규 등록이 막혔다.**
`401 Scopes are Empty`. 키를 다시 받을 방법이 없어 출처를 껐다
(`status=DISABLED`, 이유는 `settings.disabled_reason`). RSS 로 대체했다.

**법제처 OPEN API 에 입법예고가 없다.** 191개 서비스 목록을 확인했다.
공공데이터포털에서 따로 활용신청해야 한다 — 사용자 몫이다.

**GROQ 무료 티어의 진짜 벽은 분당이 아니라 하루치다.**

실측값이다.

    분당(TPM)   8,000 토큰
    하루(TPD)   200,000 토큰
    한글        1자당 0.68 토큰

요약 한 건이 원문 6,000자 기준 4,000토큰쯤 들고, 여기에 시스템 프롬프트와
출력이 붙는다. 그래서 **하루에 30~40건**이 한계다. 남은 205건을 다 채우려면
닷새쯤 걸린다.

한동안 이 벽을 잘못 읽었다. 429 를 전부 분당 한도로 다뤄서 화면에
"분당 한도를 계속 초과합니다" 가 떴고, 그걸 보고 호출이 너무 큰 줄 알아
원문 자르는 쪽을 팠다. 실제 응답 본문은 다른 말을 하고 있었다.

    on tokens per day (TPD): Limit 200000, Used 199862

기다려도 오늘은 안 풀리는 것이었다. 90초씩 세 번 기다린 뒤 실패하기를
아홉 번 반복했으니 40분을 그냥 버렸다. 지금은 둘을 갈라서, 하루치가
떨어지면 즉시 멈추고 그렇게 말한다.

**교훈은 코드가 아니라 메시지에 있다.** 오류 문구가 틀리면 고치는
사람도 엉뚱한 데를 판다.

**국세청·기재부 해석은 본문을 못 받는다.**
목록(`ntsCgmExpc`·`moefCgmExpc`)은 JSON 인데 상세는 HTML 안내 페이지가
온다. 안건명·안건번호·해석일자·원문 링크까지가 우리가 가질 수 있는 전부다.
그래서 이 종류는 "이런 해석이 있다" 까지만 말하고 원문으로 보낸다.

**판례(`prec`)는 제목이 없다.**
목록에 사건번호·법원명·선고일자는 있는데 사건명이 없다. 제목을 만들 수
없으니 목록에 올릴 수가 없고, 상세도 JSON 이 아니다. 붙이려면 다른
경로를 찾아야 한다.

**법제처 해석(`expc`)은 전문을 준다.** 질의요지·회답·이유가 다 온다.
다만 전 부처 해석이라 세무 건이 드물다 — 붙일 값은 있지만 순서는 뒤다.

**크롤링 차단은 우회하지 않는다.** robots.txt·CAPTCHA·로그인·IP·UA
어느 것도 건드리지 않는다. 수집기는 `TaxBriefing/1.0` 으로 정직하게
자기를 밝힌다. 이건 기술 문제가 아니라 지켜야 할 선이다.

## 다음 단계

### 1. 남은 요약 채우기 — 지금 화면에 빈 자리가 있다

시행예정 법령 24건이 아직 자동 생성 문구를 달고 있다.

    「소득세법 시행규칙」이(가) 일부개정되어 2026년 7월 1일부터 시행됩니다.

법령명을 한 번 더 말할 뿐 새로 알려주는 게 없다. 목록에서 이 줄을 보면
열어볼지 말지 판단이 안 된다.

`python -u -m app.summarize --limit 10 --pace 20` 을 한도가 풀릴 때마다
반복한다. 심판례·해석례는 대상에서 빠져 있으므로 법령·법안만 돈다.

### 2. 국회 법안 62건 점검

법안은 **아직 법이 아니다.** 그래서 두 가지를 확인해야 한다.

- 상태(`BILL_PROPOSED` / `ASSEMBLY_PASSED`)가 실제 `PROC_RESULT` 와
  맞는가. 통과되지 않은 법안이 "통과" 로 보이면 사장님이 미리 준비하다
  헛돈다.
- 요약이 "이렇게 바뀝니다" 가 아니라 "이런 법안이 발의됐습니다" 로
  읽히는가. 법안에 확정 어투를 쓰면 그게 가장 위험한 거짓말이다.

### 3. 텔레그램 다이제스트에 새 종류 반영

지금 다이제스트는 법령만 있던 시절에 만들어졌다. 심판례와 법안이
들어오면 어떻게 나가는지 확인하고, 종류에 맞는 말로 고친다.
심판례에 "시행" 이라는 단어가 붙으면 안 된다.

### 4. 세무 일정 (신고·납부 마감)

실무자가 가장 자주 보는 것은 사실 달력이다. 부가세 예정·확정신고,
원천세, 법인세, 종소세, 연말정산. 날짜는 법에 정해져 있어 **AI 가
지어낼 여지가 없다.**

다만 업종·과세유형에 따라 해당 여부가 갈리므로, "이 사업자는 언제"
까지 말하려면 고객 정보가 필요하다. 그건 아래 5번이다. 그 전까지는
**전체 일정만** 보여준다 — 사장님이 자기 것을 고른다.

### 5. 고객 매칭 — 데이터가 생긴 뒤에

개편안에 있던 client_profiles 는 **만들지 않는다.** 사업자 정보가
아직 없기 때문이다. 없는 데이터로 화면을 만들면 가짜 숫자를 넣게 되고,
가짜 숫자는 한 번 보이는 순간 나머지 진짜 숫자까지 못 믿게 만든다.

먼저 정해야 할 것: 사업자 정보를 어디까지 담을 것인가(상호·업종·과세
유형까지인가, 사업자번호까지인가), 그 정보를 누가 넣는가, 개인정보
처리 근거는 무엇인가. 이건 개발이 아니라 사용자가 정할 문제다.

### 6. 국세청 해석례·판례

`expc`(법령해석례), `prec`(판례) 를 붙인다. 다만 **본문이 없는 출처에는
AI 를 쓰지 않는다.** 제목만 주고 쟁점을 쓰라고 하면 그건 지어내는 것이다.
전문이 오는 것만 심판례처럼 구조를 갈라 보여주고, 아니면 제목과 링크만
둔다.

## 일하는 방식

이 프로젝트에서 반복해서 배운 것들이다.

**화면을 고쳤으면 실제로 렌더링해서 눈으로 본다.**
`tsc` 통과가 화면이 뜬다는 뜻이 아니다. JSX 주석 하나로 빌드가 깨졌는데
타입 검사는 통과했고, 그 상태로 자동 점검은 "가로 넘침 없음" 을 찍었다.
에러 페이지의 가로 폭을 재고 있었던 것이다.

**세는 것은 화면이 아니라 전체를 센다.**
"시행예정 15" 가 실제로는 34건이었고, 결론 필터가 전부 0 이었다.
둘 다 불러온 페이지 안에서 셌기 때문이다. 건수는 서버에 묻는다.

**모르는 것은 비워 둔다. 채우면 거짓이 된다.**
심판례 의결일이 비어 있길래 화면이 오늘 날짜를 넣었고, 3주 전 결정이
오늘 나온 것처럼 보였다. 값이 없으면 칸을 뺀다.

**AI 는 태그만 하고 지우지 않는다.**
모델이 업종을 못 붙였다고 콘텐츠를 숨겼더니 증권거래세율 인상이 화면에서
사라졌다. "판단해보니 무관" 과 "판단을 못 함" 은 다른 값이어야 한다.

**종류가 다르면 말도 달라야 한다.**
심판례에 "개정되어 시행됩니다", "지금 해야 할 일", "확정 아님" 이
붙어 있었다. 셋 다 거짓이다. 심판례는 이미 끝난 남의 사건이다.

**자를 때는 자른 사실을 같이 적는다.**
조문 40개만 보여주고 조용히 있으면 "이게 전부" 로 읽힌다. 실제로는
277개였다.
